# RAG 智能文档问答系统
## 项目简介
基于 FastAPI + FAISS 向量库 + SQLite 构建的生产级检索增强生成（RAG）问答系统。后端采用分层架构设计，实现文档上传、文本切分、向量化检索、大模型增强回答全链路能力；配套全链路日志埋点、全局统一异常处理与关系型数据持久化，完成从 Demo 到工程化项目的升级。前端提供 Streamlit 可视化交互界面，支持对话式问答与引用来源溯源。项目已完成多组参数消融实验，调优出最优分块与检索策略，回答准确性与可解释性显著提升。
## 技术栈
* Web 框架：FastAPI + Uvicorn（ASGI 高性能服务）
* 前端界面：Streamlit（快速构建可视化交互页面）
* 向量检索：FAISS 本地向量数据库，实现高效相似度匹配
* 关系型数据库：SQLite + SQLAlchemy ORM，实现文档、会话、消息全链路结构化数据持久化
* 文本处理：LangChain 文本切分器，支持自定义分块粒度
* 配置管理：python-dotenv + 环境变量（密钥硬编码零侵入）
* 模型对接：兼容 OpenAI 协议的大模型 API（DeepSeek、通义千问等主流厂商均可适配）
* 响应模式：同步一次性返回 + SSE 流式输出双模式支持
* 工程化体系：Python logging 全链路日志、自定义业务异常、全局统一异常处理
* 存储架构：向量库存语义特征 + 关系库存业务数据的双库存储架构

## 环境准备与安装
### 1. 环境要求
Python 3.9 及以上版本
### 2. 创建并激活虚拟环境
```bash
#在项目根目录新建虚拟环境
python -m venv venv
#Windows 系统激活虚拟环境
venv\Scripts\activate
#Mac / Linux 系统激活虚拟环境
source venv/bin/activate
```

### 3. 安装项目依赖
```bash
pip install fastapi uvicorn python-dotenv requests langchain faiss-cpu streamlit
```

### 4. 配置环境变量
在项目根目录新建 .env 文件,填入你的大模型配置信息:
```env
LLM_API_KEY=你的大模型API密钥
LLM_BASE_URL=https://api.deepseek.com/v1
LLM_MODEL_NAME=deepseek-chat
EMBEDDING_API_KEY=你的向量模型API密钥
EMBEDDING_BASE_URL=向量模型接口地址
EMBEDDING_MODEL=text-embedding-v2
```


* 请求方式:POST

* 请求方式:POST
* 接口路径:/chat/stream

* 请求体:

## 系统架构与数据流转
1. 分层架构设计
项目采用经典的三层架构，各层职责单一、解耦清晰，便于扩展与维护：
接口层（api）：负责接收 HTTP 请求、参数校验、响应封装，不包含业务逻辑
业务层（services）：封装核心业务逻辑，包括大模型调用、文本处理、向量检索等
数据层（models + core）：负责数据库模型定义、数据库连接、配置管理、日志与异常等基础组件
2. 核心数据流转
文档上传流程
前端上传文件 → 接口层接收并读取文件内容 → 业务层完成文本切分与向量化 → 向量存入 FAISS 向量库 → 文档元数据写入 SQLite 数据库 → 返回上传结果与文档 ID
问答交互流程
用户提交问题与会话 ID → 问题向量化后检索 Top-K 相似片段 → 拼接 Prompt 调用大模型生成回答 → 用户问题与 AI 回答同步写入消息表 → 返回回答内容、引用来源与会话 ID
3. 数据库设计
共设计 4 张核心业务表，覆盖用户、文档、会话、消息全链路：
users：用户基础信息表，支撑多用户场景扩展
documents：上传文档元数据表，记录文件名、分块数量、文件大小、上传时间
conversations：会话表，隔离不同对话主题，关联用户
messages：消息表，存储每一轮的用户提问与 AI 回答，关联会话

### 4.3 实验结论与分析
1. chunk_size=500 + Top-K=1，综合平均分最高（4.67），为本次实验的最优配置。该分段长度适中，单条召回即可包含全部答案知识点，冗余信息最少，回答完整性与准确性表现均衡。
2. Chunk_size过小的问题：当chunk_size=300时，单条片段信息断裂、上下文不完整，即使增大Top-K多段拼接，也只能小幅提升完整性，整体效果上限极低，无法达到理想的问答效果。
3. Chunk_size过大的问题：当chunk_size=800时，单条文本自带大量无关内容，继续调高Top-K会叠加更多冗余上下文，导致回答冗余度持续上升，分数持续下降。
4. Top-K核心规律：并非召回数量越多（K值越大）效果越好，Top-K的取值必须与文本分段粒度匹配。适中的chunk_size搭配最小的Top-K=1，反而能达到最优的问答效果。
### 实验步骤说明
本实验采用消融实验方案，分别对 `chunk_size` 文本分段大小、`Top-K` 召回片段数量两个变量进行对照测试，完整操作流程如下：

1. 修改代码文件 `splitter_service.py` 中的 `chunk_size` 参数，依次设置为 300、500、800 三组。
2. 删除项目目录下的向量库持久化文件 `index.faiss`、`index.pkl`，清空历史向量索引，避免旧数据干扰实验结果。
3. 重启 FastAPI 后端服务，重新上传《德州中燃城市燃气发展有限公司工作规则.txt》文档，完成新一轮文本切割与向量化入库。
4. 固定8道相同的测试问题，分别搭配 `Top-K = 1、2、3` 三种召回策略进行提问，按照三项指标打分并记录数据：
   - 回答完整性（1~5分）
   - 回答准确性（1~5分）
   - 内容冗余度（1~5分）
5. 更换 `chunk_size` 或 `Top-K` 参数，重复步骤2~4，完成全部9组参数组合测试。
6. 汇总所有评分数据，计算每组平均分，对比分析最优参数组合与实验规律。
